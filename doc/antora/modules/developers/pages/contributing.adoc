= Contributing

Contributions can include code, tests, documentation fixes, issue
reports, and design proposals. The goal is to make each contribution
understandable and independently reviewable.

The repository's `.github/contributing.md` file describes
submission channels, defect reporting, verification, and review
expectations.

== Propose a Change

GitHub pull requests are the preferred way to submit source and
documentation changes. The
xref:gitpr.adoc[Pull Request Guide] explains how to propose changes
using a fork and a branch, including edits made in GitHub's web editor.

For a small patch when GitHub is unavailable, see
xref:email.adoc[Submitting a Patch by Email]. Email submissions may
require additional coordination for review.

Early discussion can help with substantial changes, especially new
modules or changes to shared interfaces, but it is not a requirement
for submitting a proposal.

== Describe Your Change

Explain what problem the change addresses, what behavior or
documentation it modifies, and what verification you performed.
Include actual test results or steps used to check documentation
references. Identify any checks that were not performed.

Descriptions such as "fix bug" or "update file" provide too little
information to evaluate the change without reading every line.

== Keep Changes Focused

Separate unrelated changes so that each can be evaluated on its own.
A single logical change may legitimately affect several files,
including source, tests, and documentation.

When one change depends on another, describe the dependency in the
pull request or commit message. Keep unrelated whitespace or
formatting changes separate so they do not obscure the functional
difference.

== Review and Follow-up

A pull request begins a review; it is not an automatic request for
permission to contribute. Reviewers may ask questions, propose
alternatives, or request tests. Where an existing solution or design
constraint is cited, a link or concrete explanation makes feedback
more actionable.

Technical claims and verification should be evaluated on their
merits, regardless of how the change was drafted. The repository's `.github/contributing.md` file covers additional
expectations.
