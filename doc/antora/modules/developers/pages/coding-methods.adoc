= Coding Methods

These guidelines describe practical approaches to writing code that
can be reviewed, tested, and maintained. They complement the project's
coding style and naming conventions.

Coding standards apply to function names, the look of the code, and
coding consistency. Coding methods apply to the daily practices used
by the programmer to write code.

== 1. Comment your code

Document non-obvious decisions, invariants, ownership, and assumptions.
Useful comments explain why an implementation exists, not merely what
a straightforward statement does.

For FreeRADIUS, use doxygen `@`-style comments so you get the benefits
of the developer documentation site, https://doc.freeradius.org/.

[#_give_things_reasonable_names]
== 2. Give things reasonable names

Choose names that describe their purpose in context. Short names can
be appropriate for limited scopes, but ambiguous names make larger
sections harder to review and maintain.

Avoid smurfs. Don't reuse struct names in field names, i. e.

[source,c]
----
struct smurf {
  char *smurf_pappa_smurf;
};
----

Prefer names that make behavior understandable without requiring
readers to reconstruct it from unrelated code.

[#_check_input_parameters_in_the_functions_you_write]
== 3. Check input parameters in the functions you write

Validate inputs at appropriate boundaries and handle invalid input
with a useful error where recovery is expected.

Use `assert()` or `fr_assert()` for programmer invariants and states
that should not occur in correct code; assertions are not substitutes
for checking untrusted or recoverable input.

[NOTE]
====
Invalid input should produce an actionable error when feasible,
rather than silently propagating an invalid state.
====

[#_write_useful_error_messages]
== 4. Write useful error messages

Include the failed operation and relevant context in error messages,
while avoiding disclosure of secrets. When diagnostic instrumentation
proves generally useful, retain it for future debugging.

== 5. Check error conditions from the functions you call

Check return values from called functions and handle errors before
using outputs that may be invalid.

One of the most common mistakes is:

[source,c]
----
fp = fopen(...);
fgetc(fp);       /* core dumps! */
----

Check `fp` for `NULL` before use and return or record a useful
error when opening a file fails.

== 6. Handle unexpected failures deliberately

Check recoverable error conditions and report them through the
appropriate error-handling path. A crash is evidence to investigate,
not a measure of the contributor's competence.

Assertions can make violations of internal invariants visible during
testing. Use them when termination is appropriate for an impossible
state, not as a replacement for routine validation or recovery.

[#_initialize_your_variables]
== 7. Initialize your variables

`memset()` (`talloc_zero()`) is your friend. `ptr = NULL` is nice,
too.

Having variables containing garbage values makes it easy for the code
to do garbage things. The contents of local variables are inputs to
your function. See
xref:#_check_input_parameters_in_the_functions_you_write[#3].

It's also nearly impossible for you to debug any problems, as you
can't tell the variables with garbage values from the real ones.

== 8. Don't allow buffer over-runs

They're usually accidental, but they cause core dumps. `strcpy()` and
`strcat()` are ugly. Use them under duress.

`sizeof()` is your friend.

== 9. `const` is your friend

If you don't mean to modify an input structure to your function,
declare it `const`. Declare string constants `const`. It can't hurt,
and it allows more errors to be found at compile time.

Use `const` everywhere. Once you throw a few into your code, and have
it save you from nonsensical bugs, you'll blindly throw in `const`
everywhere. It's a life-saver.

== 10. Use C compiler warnings

Turn on all of the C compiler warnings possible. You might have to
turn some off due to broken system header files, though. But the more
warnings the merrier.

Getting error messages at compile time is much preferable to getting
core dumps at run time. See xref:#_initialize_your_variables[#7].

Notice that the C compiler error messages are helpful? You should
write error messages like this, too. See
xref:#_write_useful_error_messages[#4].

== 11. Avoid UNIXisms and ASCIIisms and visualisms

You don't know under what system someone will try to run your code.
Don't demand that others use the same OS or character set as you use.

For clarity, use `NULL` when representing a null pointer in C.
The integer constant `0` is also a valid null pointer constant in C,
so this is a readability convention rather than a claim about a
platform's address zero.

Use `'\0'` to make a terminating null character explicit in code.
For `memset()`, the fill argument is an integer byte value; use `0`
when zeroing memory, and prefer typed initialization when appropriate.

Don't put tabs in string constants, either. Always use `'\t'` to
represent a tab, instead of ASCII 9. Literal tabs are presented to
readers of your code as arbitrary whitespace, and it's easy to mess
up.

== 12. Make conditionals explicit

Though it's legal to test `if (foo) {}` if you test against the
appropriate value (like `NULL` or `'\0'`), your code is prettier and
easier for others to read without having to eyeball your prototypes
continuously to figure out what you're doing (especially if your
variables aren't well-named). See
xref:#_give_things_reasonable_names[#2].

== 13. Test your code

Even Donald Knuth writes buggy code. You'll never find all of the bugs
in your code. But writing a test program definitely helps.

This means that you'll have to write your code so that it will be
easily testable. As a result, it will look better and be easier to
debug.

== 14. Hints, Tips, and Tricks

This section lists many of the common `rules` associated with code
submitted to the project. There are always exceptions, but you must
have a really good reason for doing so.

=== Read the Documentation and follow the CodingStyle

The FreeRADIUS server has a common coding style. Use real tabs to
indent. There is whitespace in variable assignments (`i = 1`, not
`i=1`).

When in doubt, follow the conventions of nearby code and the
xref:coding_standards.adoc[coding standards]. If a change needs an
intentional exception, explain it in the pull request so reviewers
can evaluate the reason.

=== #ifdefs are ugly

Code cluttered with `#ifdef` s is difficult to read and maintain.
Don't do it. Instead, put your `#ifdef` s in a header, and
conditionally define `static inline` functions, or macros, which are
used in the code. Let the compiler optimize away the 'no-op' case.

Simple example, of poor code:

[source,c]
----
#ifdef CONFIG_MY_FUNKINESS
  init_my_stuff(foo);
#endif
----

Cleaned-up example:

(in header):

[source,c]
----
#ifndef CONFIG_MY_FUNKINESS
  static inline void init_my_stuff(char *foo) {}
#endif
----

(in the code itself):

[source,c]
----
init_my_stuff(dev);
----

=== `static inline` is better than a macro

Static inline functions are greatly preferred over macros. They
provide type safety, have no length limitations, no formatting
limitations, and under gcc they are as cheap as macros.

Macros should only be used for cases where a static inline is clearly
suboptimal (there a few, isolated cases of this in fast paths), or
where it is impossible to use a static inline function (such as
string-izing).

`static inline` is preferred over `$$static __inline__$$`, `extern
inline`, and `$$extern __inline__$$`.

=== Keep the Design Proportional to the Problem

Implement the behavior that is needed and supported by the current
requirements. Avoid speculative abstractions that make the code
harder to understand without a demonstrated benefit.

Separate responsibilities when doing so improves cohesion, testing,
and maintenance. Excessive decomposition can also obscure the flow
of a program.

[TIP]
====
Apply the same principle to documentation: put information where
readers need it, avoid unnecessary duplication, and link to a
canonical explanation when appropriate.
====
